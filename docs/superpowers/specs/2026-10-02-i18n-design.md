# App-wide Internationalization (Web + Mobile)

Status: design
Depends on: nothing. Independent of the mobile admin engine phases.

This spec defines a shared, config-driven translation system so that every
user-facing string in the **web** (`apps/web`, Next.js) and **mobile**
(`apps/mobile`, Expo/React Native) apps can be translated. Adding a new language
must be as simple as dropping in one catalog file.

## Goal

- Make the full web and mobile apps translatable.
- Adding a language = adding one file; adding translations = editing that file.
- No backend changes and no user-data translation.
- Ship a single source of truth shared by both apps.

## Decisions (confirmed during brainstorming)

| Question | Decision |
|---|---|
| Target apps | Both web and mobile |
| Languages | Many languages; infrastructure must scale by adding files. Ship `en` (source of truth) + `ur` as proof. |
| Active language selection | Device/browser only, stored locally. No backend/profile change. |
| Key style | Semantic keys (e.g. `auth.login.title`) |
| Sequencing | Phase 1: full mobile + web foundation; remaining web pages in follow-up batches |

## Architecture

Approach A: a shared workspace package **`@eis/i18n`** that owns the translation
engine, the locale registry, and all catalogs. Web and mobile consume the same
package, mirroring the existing `@eis/appearance` pattern (TS source consumed
directly; Next transpiles it via `transpilePackages`, Metro resolves it as a
workspace dependency).

Platform differences are injected, not baked in:

- **Storage adapter** — AsyncStorage on mobile, `localStorage` on web.
- **Locale detector** — `expo-localization` on mobile, `navigator.languages` on
  web.

```
                    ┌─────────────────────┐
                    │     @eis/i18n       │
                    │  Translation Engine │
                    │  Locale Registry    │
                    │  Catalogs           │
                    │  Plurals            │
                    │  Formatters         │
                    │  React bindings     │
                    └─────────┬───────────┘
                              │
                 ┌────────────┴────────────┐
          ┌──────▼──────┐           ┌──────▼──────┐
          │    Web      │           │   Mobile    │
          │   Next.js   │           │ Expo/RN     │
          └──────┬──────┘           └──────┬──────┘
                 │                         │
          localStorage              AsyncStorage
          navigator.languages       expo-localization
```

Conceptual layering inside the package:

```
@eis/i18n
├── core engine        -> no dependencies
├── locale registry    -> no dependencies
├── formatters         -> Intl only
├── storage types      -> no dependencies
└── React bindings     -> React peer dependency
```

React is declared as a `peerDependencies` entry and kept out of `dependencies`.

## Catalog format

Keys are flat, dot-notation, semantic strings with established namespaces
(see below). Nesting is not used, which keeps plural suffixing and generation
simple. Catalogs live in `src/locales/`.

**`en.ts` is the source of truth and the schema.** It is TypeScript so it can be
validated and derived from:

```ts
// src/locales/en.ts
export const en = {
  "common.save": "Save",
  "common.cancel": "Cancel",
  "auth.login.title": "Sign in",
  "students.count.one": "{{count}} student",
  "students.count.other": "{{count}} students",
  // ...
} as const;
```

**Every other locale is one JSON file** in the same directory, with metadata and
messages kept conceptually separate:

```json
{
  "$meta": { "name": "Urdu", "nativeName": "اردو", "dir": "rtl" },
  "common.save": "محفوظ کریں"
}
```

Types:

```ts
export interface LocaleMeta {
  code: string;
  name: string;
  nativeName: string;
  dir: "ltr" | "rtl";
}

export type Messages = Record<string, string>; // raw messages, including plural-suffixed keys

// JSON catalogs: $meta (code supplied by the generator) plus a partial message map
export type LocaleCatalog = { $meta: Omit<LocaleMeta, "code"> } & Partial<Messages>;
```

The generator extracts `$meta`, attaches the `code` from the filename, and
produces `LOCALES` with fully qualified entries:

```ts
export const LOCALES: LocaleMeta[] = [
  { code: "en", name: "English", nativeName: "English", dir: "ltr" },
  { code: "ur", name: "Urdu", nativeName: "اردو", dir: "rtl" },
];
```

**Add-a-language workflow**

1. Add `src/locales/<code>.json` with a `$meta` block.
2. Run `pnpm --filter @eis/i18n gen`.

The generator scans `src/locales/*.json` only; `en.ts` is handled separately as
the schema. It validates every defined key against `en`, warns on unknown keys,
and writes `src/locales/index.ts`. The generated file is committed; there is no
runtime build step.

## Engine (`translate.ts`)

`createTranslator(locale, messages, fallbackMessages)` returns `t(key, params?)`,
where `key` is a generated `MessageKey`.

- **Interpolation**: `{{name}}` placeholders replaced from `params`.
- **Plurals**: `t("students.count", { count })` looks up the plural family
  described below.
- **Fallback**: exact resolution order for plurals is defined below.
- **Direction**: `dir` comes from locale meta (`ltr` default; `rtl` for `ur`,
  `ar`, `he`, `fa`, ...); `isRTL` is exposed.

### Plural keys and typing

Raw catalogs store plural variants as suffixed keys:

```
students.count.one   -> "{{count}} student"
students.count.other -> "{{count}} students"
```

The generator recognizes the plural category suffixes
`zero | one | two | few | many | other` and **collapses** each family to its
base key. Generated `MessageKey` therefore contains `students.count`, not the
suffixed variants, so the call site:

```ts
t("students.count", { count })
```

is compile-time checked. A single semantic key intentionally ending in one of
those words is not supported; the convention is to avoid category words as a
terminal key segment.

`t` accepts `Record<string, string | number>` as `params`.

### Plural fallback resolution

Given base key `K`, locale `L`, plural category `C`, and English fallback `en`:

```
1. L + K.C
2. en + K.C
3. L + K            (base key without category)
4. en + K
5. raw key string
```

Steps 3/4 make partially translated plural catalogs predictable: a locale that
provides only some categories still resolves, and a locale that provides no
plural variants falls back to its base key or English.

## Locale detection and normalization (`detect.ts`)

Device/browser tags are normalized before matching: lowercased and `_` replaced
with `-`. `pickBestLocale(supported, candidates)` then resolves in order:

```
1. exact tag match          ("ur-pk" == "ur-pk")
2. language-region match    (candidate "ur-pk" -> supported "ur-pk")
3. language-only match      (candidate "ur-pk" -> supported "ur")
4. default locale           ("en")
```

Example: `pickBestLocale(["en", "ur"], ["ur-PK", "en-US"])` returns `"ur"`.
This matters in practice because Pakistani browsers/devices commonly report
`ur-PK` rather than `ur`.

## React bindings (`LocaleContext.tsx`)

```tsx
<I18nProvider storage={adapter} detect={detectFn} defaultLocale="en">
  {children}
</I18nProvider>
```

- On mount (client-side): read persisted locale -> run `detect` -> `defaultLocale`.
- `setLocale(code)` updates React state and persists via the storage adapter.
- Persistence is always delegated to the injected storage adapter; the provider
  only additionally reflects the locale on the host document when one exists
  (web: sets `document.documentElement.lang` and `dir`).
- `useTranslation()` returns
  `{ t, locale, setLocale, dir, isRTL, formatDate, formatDateTime, formatTime, formatNumber, formatCurrency }`.
- `t` is memoized per locale so it is stable across renders.
- `dir`, `isRTL`, and `locale` are exposed for all consumers; the provider does
  not assume `dir` alone restyles native layouts.

### SSR / hydration (web)

Detection and persistence are client-only. The adapter and detector must never
touch `window`, `localStorage`, `navigator`, or `document` at module
initialization:

```ts
export const webStorage: StorageAdapter = {
  get(key) {
    if (typeof window === "undefined") return null;
    return window.localStorage.getItem(key);
  },
  set(key, value) {
    if (typeof window === "undefined") return;
    window.localStorage.setItem(key, value);
  },
};
```

First paint behavior is deliberate for Phase 1:

```
server render      -> English / LTR
hydration          -> English / LTR
after mount effect -> stored preference applied (e.g. Urdu / RTL)
```

A brief flash from LTR to RTL is accepted. Eliminating it requires reading the
preference server-side (cookie); that is explicitly deferred and would conflict
with the local-only decision for this phase.

### React Native direction

Changing `dir` to `"rtl"` does not flip a native layout. `I18nManager.forceRTL`
only takes effect after an app reload. Phase 1 exposes `dir`/`isRTL` and applies
web `dir` immediately; true native RTL layout remains a documented follow-up.

## Platform adapters and wiring

### Mobile

- Dependency: `expo-localization` (SDK-matched, installed with
  `npx expo install expo-localization`) for device locale detection; `Intl` is
  used for formatting/plurals (available on Hermes in RN 0.86).
- Storage: `AsyncStorage` under key `eis.locale`.
- Wrap the app in `App.tsx`: `<ThemeProvider><I18nProvider ...><AppInner/>...`.
- Add a **Language** section to the existing `AppearanceModal` (list of
  registered locales using `nativeName`, with the active one checked).

### Web

- Add `"@eis/i18n"` to `next.config` `transpilePackages`.
- Wrap the root layout in `<I18nProvider>`, using the SSR-safe adapter above.
- Storage: `localStorage` under key `eis.locale`.
- Detection: `navigator.languages`, executed client-side.
- Add a `<LanguageSwitcher>` to the nav/header (select of registered locales).
- The provider sets `dir` on `<html>`, so RTL layouts apply after hydration.

## Mobile admin-engine labels

The admin engine (`apps/mobile/src/admin/`) stores static English labels in
`registry.ts`, `nav.ts`, and `screens.ts`. These become **message keys**, and
the rendering components translate them at render time:

- `registry.ts` module `label`, `column.label`, `field.label`, option
  `label`s, and section `label`s store keys (e.g. `admin.students.label`).
- `ModuleListScreen`, `ModuleFormScreen`, `ModuleDetailScreen`, `Sidebar`,
  `AppHeader`, and the option-rendering fields call `t()` on those keys.
- `nav.ts` section/item labels and `screens.ts` custom-screen labels likewise
  use keys.

This is mechanical but broad and forms the bulk of the mobile work. No behavior
changes; only the source of displayed text changes.

## Formatter localization

Both apps currently hardcode `en-US`/`en-GB` in `src/lib/format.ts`. They will
delegate to the locale-aware helpers from `@eis/i18n`, bound to the active
locale via `useTranslation()`. Call sites that pass a record value keep their
signatures; only the internal formatting uses the active locale.

`formatCurrency` takes an options object with a default, so it stays future
proof without changing call sites:

```ts
formatCurrency(value, { currency = "PKR", locale }?: { currency?: string; locale?: string })
```

`formatCurrency(150000)` uses PKR today; `formatCurrency(150000, { currency: "USD" })`
is available later.

## Tooling

- `pnpm --filter @eis/i18n gen` — regenerate `src/locales/index.ts` (registry +
  `MessageKey`) after adding or editing catalog files.
- `pnpm --filter @eis/i18n check` — validation report:
  - `en`: no invalid keys (including no unknown plural category suffixes).
  - other locales: no unknown keys, missing keys explicitly listed, and each
    missing key documented as falling back to English.
  - all locales: valid `$meta`, valid placeholders (placeholder set must match
    `en` for the same key), and valid plural structure (category suffixes must
    be a subset of the families defined in `en`).
- `packages/i18n/README.md` — concise guide: add a language, add keys, plural
  suffix conventions, namespace list, RTL note.

## Scope of this phase

1. `@eis/i18n` package: engine, types, detection, storage, formatters, React
   bindings, generator/checker, `en` catalog, `ur` proof, README.
2. **Mobile full**: convert all user-visible strings in `apps/mobile/src` and
   `App.tsx` (screens, components, admin engine labels/options/sections,
   formatters) and add the language picker.
3. **Web foundation**: provider, detection, persistence, `LanguageSwitcher`,
   `next.config`, and conversion of the shell — `src/lib/nav.ts`,
   `src/lib/auth.tsx`, `src/components/{ui,Pagination,PermissionGate}.tsx`, the
   login page, and the dashboard layout/header.
4. Tooling, generated registry, and translation guide.

## Verification

- `packages/i18n`: `tsc --noEmit` clean; `gen` is idempotent; `check` passes with
  the rules below.
- **Catalog validation** (`check`):
  - `en`: no invalid keys.
  - `ur` and every other locale: no unknown keys; missing keys explicitly
    reported; missing keys fall back to `en`.
  - all locales: valid metadata, matching placeholder contracts vs `en`, and
    valid plural structures. A placeholder mismatch such as English
    `"Welcome, {{name}}"` vs Urdu `"خوش آمدید {{username}}"` is reported.
- Mobile: `tsc --noEmit` clean; `expo lint` clean; Metro web bundle returns 200.
- Web: `next build` (or `next lint` if build is unavailable) exits clean;
  TypeScript clean.
- Runtime: switch between `en` and `ur`; verify the choice persists across
  reload/restart; verify a missing key falls back to English; verify web
  `<html dir="rtl">` flips for Urdu after hydration.
- Mobile + web only, so after implementation run `deploy-edu.sh` (web is
  deployed; no API migration).

## Out of scope

- Backend/API validation and error messages (stay English; field labels shown
  by the UI are translated, but server `message` strings are not).
- Translating user-entered data (names, notes, etc.).
- Full native RTL layout parity on mobile (see React Native direction above).
- Server-side locale rendering / cookie-based preference (deferred; would remove
  the first-paint flash).
- Page-by-page conversion of the remaining web dashboard pages, which proceed
  as follow-up batches using the established pattern.

## Risks and mitigations

- **Large mechanical surface (web 379 files / mobile 54 files).** Mitigated by
  sequencing: full mobile + web foundation first, remaining web pages batched.
- **Stale registry after adding a language.** Mitigated by `gen` and `check`,
  and by committing the generated file.
- **`Intl.PluralRules`/`Intl` gaps on old runtimes.** RN 0.86 Hermes ships full
  `Intl`; the engine falls back to the base key if plural categories are
  unavailable.
- **Translations lag behind new keys.** `check` reports missing keys per locale
  and the fallback chain prevents raw keys or blanks from appearing.
- **Hydration mismatch from client-only preference.** Avoided by rendering the
  server/default locale on first paint and applying the stored locale in an
  effect; only a benign LTR->RTL flash remains (accepted, cookie follow-up).
